# 开发时约束条件

## 一、Debug 模式

### 适用范围

- 除最终设计 UI 阶段外，所有基础架构和判断内核的测试
- 整个项目始终保留 debug 模式

### 行为要求

- 所有行为和涉及到的结果变量在命令行中输出
- 不碰 UI
- debug 模式不开窗口、不初始化 UI、不依赖前端
- 项目完成后用户点击 exe 或用命令行正常打开程序时正常进入 UI

### 启动方式

- 统一用 `debug-<模块名>` 形式的子命令（或等价方式）
- 参数约束：
  - 只在确实需要时加参数
  - 不要为了加而加
  - 参数命名要有意义
  - 每个模块在"需要人工验证"的输出里，必须说明该模块 debug 模式支持哪些参数、分别干什么

### 输出字段

- 每个阶段/每个模块自己定义要打印什么字段
- 原则：把该模块所有内部状态和判断结果都打出来，方便肉眼验证逻辑对不对

### 验收标准

- 每个模块完成后，必须能在 debug 模式下肉眼验证
- 不允许用"单元测试通过"作为唯一验收标准

---

## 二、人工验证

### 触发时机

- 做好每一个模块后

### 行为要求

- 需要人工肉眼测试时，必须显式声明并停止当前轮次
- 不要啥都不说唤醒一次程序之后用户也不知道要干啥
- 用户关掉程序后如果没反馈，不要判定进程自动结束，也不会发现真实问题

### 禁止事项

- 不要自己运行程序后，看到 exit code 0 就判定"验证通过"
- 不要在没有人工反馈的情况下，把"我运行了没报错"当作"功能正确"

### 输出格式

``` txt
【需要人工验证】
请运行：<完整命令>
预期看到：<具体描述终端输出或 UI 表现>
判定标准：
  正确：<什么样算对>
  错误：<什么样算错>
我无法自己验证的原因：<例如：需要实际打开浏览器、需要观察终端打印>
```

输出后停止本轮对话，收到用户反馈后再继续下一轮。

---

## 三、动手前先确认（方案阶段）

### 触发时机

- 任何超过 1 个文件的改动
- 任何涉及架构决策的改动
- 任何可能影响其他模块的改动

### 行为要求

先输出方案并结束本轮，等用户查阅确认。

方案必须包含：

- 改哪些文件（精确到文件路径）
- 改什么逻辑（用一两句话说明）
- 有没有架构决策（如果有，列出选项和推荐）
- 为什么这么改（一句话理由）

用户回复"准了"才能开始改。

### 修改过程中

- 如果需要跑测试或需要用户确认，随时提出
- 不要怕问得太频繁
- 不要自己判断"应该没事"就跳过

### 修改完成后

输出"怎么验证"并结束本轮：

- 运行什么命令
- 预期看到什么
- 什么样算对、什么样算错

用户亲自核验通过后，才会说"下一个"，再进下一个任务。

### 方案被否决时

先问"不行在哪里"，不要自己猜着改。

## 四、对话管理

### 交接文档模板

``` txt
【项目】<名称>，<技术栈>
【路径】<绝对路径>

【已完成】
- <已完成的功能>

【挂账（暂不处理）】
- <问题 1>
- <问题 2>

【当前任务】
<要做的事>

【工作约定（必须遵守）】
- 改代码前先出方案，等批准
- 命令行 debug 验证，不碰 UI
- 每个模块完成必须显式输出"需要人工验证"格式，停轮
- 只拦"编译能过但运行会错"的问题
- 禁止顺手改无关文件
```

---

## 五、其他要求

### 1. 先读代码给证据，再出方案。不要凭记忆写

### 2. 只改指定文件，其余一律不动

### 3.贴出改动后的代码片段，不要笼统说"改了"

### 4.已确认的决策不要在新方案里改，除非明确说明

### 5.方案中示明本任务范围：<清单>。实施时清单外的一律不做

### 6.方案不超过 30 行
